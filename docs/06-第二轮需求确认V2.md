## 1. 登录方式 ⚠️ 你的推断需要修正

### 1.1 短信登录「是否不容易触发风控」→ **相反，更容易**

已验证（接口文档原文）：

> 「人机验证方式登录包含**账号密码登录**与**手机短信验证码登录**」
> 「**注：扫码登录**不需要进行**人机验证**，故**不使用**以下接口」

即：

- 短信登录 **必须**先过 `passport.bilibili.com/x/passport-login/captcha?source=main_web` 拿到极验（geetest）的 `gt` / `challenge`，滑块通过后拿 `validate` / `seccode`，才能调 `web/sms/send`，再调 `web/login/sms`。
- 文档原文：「本文档为 Bilibili 文档，验证码为 geetest 极验提供，**故不提供相关 API**」——**极验没有可调用的接口**，原生 Android 端要么内嵌 WebView 渲染极验、要么接第三方打码。
- 扫码登录**完全不过人机验证**。

三条理由说明短信更差：

1. **必须实现极验**：纯 Compose 原生做不了，只能塞 WebView，且极验版本一变就废。
2. **风控评分更低**：扫码是由一个**已登录的官方客户端**主动授权的，天然带信任信号；短信登录是一个陌生设备指纹 + 陌生 UA 直接发起认证，正是 `-352` 最容易命中的场景。
3. **手机号有额度**：短信发送有频率限制，反复失败可能临时锁号。

**所以：不建议自己实现短信接口。**

### 1.2 但「手机号登录」这个入口可以有 —— 换个实现法

你的原话是「如果短信登录更优，则必须添加手机号登录的选项」。短信不更优，但我给你一个**既满足入口、又不碰风控**的做法：

> **方案：内嵌 WebView 打开 B 站官方登录页**，登录成功后从 `CookieManager` 里取 `SESSDATA` / `bili_jct` / `DedeUserID` / `buvid3`。

好处：手机号验证码、密码、扫码**全部方式都自动支持**（官方页面自己提供），极验由官方页面自己处理，我们一行验证码代码都不写，请求特征也和真实浏览器一致。这是第三方客户端里最稳的登录路径。

### 1.3 TV 登录 / Web 登录会不会把现有端踢下线

- **Web 扫码：不会踢掉你的网页端。** ✅ 高置信。B 站 Web Cookie 会话允许多端并存（同一账号在多个浏览器同时在线是日常行为）。
- **TV 扫码：不建议用，但不是因为"会踢"。** ❓ 是否互踢我无法确证（TV 登录接口带 `local_id` 设备标识，理论上不同 `local_id` 各占一个会话槽，大概率不互踢）。真正的问题是另外两条，已验证：
  1. TV appkey（`4409e2ce8ffd12b8`，云视听小电视）拿到的 `access_token`，**只能配这组 appkey/appsec 用**，否则返回 `{code: -663, message: '鉴权失败，请联系账号组'}`。会把整个接口层锁死在 TV 体系里。
  2. **TV 端可播片源和手机端不是一套**，部分内容 TV 版无版权。用 TV token 会平白丢片源。

### 1.4 建议的最终方案（等你确认）

| 优先级 | 方式 | 说明 |
|---|---|---|
| 主 | **Web 扫码登录** | 用你手机上的官方 App 扫，最顺，不过人机验证，不影响网页端 |
| 备 1 | **WebView 官方登录页**（= 手机号 / 密码 / 短信） | 满足你的"手机号登录选项"，风控最低 |
| 备 2 | **手动粘贴 Cookie** | 从浏览器 F12 复制 3 个字段。自用 App 里这是零风险兜底，10 秒搞定 |
| 不做 | TV 扫码 | 见 1.3 |

凭证存 `EncryptedSharedPreferences`（Tink），不入 Room，不写日志。

## 2. 历史缓存策略 ✅ 可行，但有两个坑要先说清

你的策略：只拉 30 天内 / 本地留 3 个月 / 7 天检查一次 / 超 3 个月自动清理。

技术上完全成立：`x/web-interface/history/cursor` 按 `view_at` 倒序游标翻页，翻到 `view_at < now-30d` 就停止，比上一轮的方案更省流量、更省风控额度。

### ⚠️ 坑 1：「只拉 30 天」和「本地留 3 个月」的数据从哪来

这两条只有在一种理解下自洽：**本地库是随时间自然沉淀出来的**——首次安装只有 30 天的数据，之后每次增量同步都往里加，三个月后本地自然积累到 3 个月。而不是"去服务端拉 3 个月回来"。

我按这个理解设计。**如果你其实是想首次安装就有 3 个月记录**，告诉我，那首次同步要放宽到 90 天（只是第一次，之后仍按 30 天增量）。

### ⚠️ 坑 2：30 天内的影视记录可能不够铺满首屏

历史里绝大部分是 UGC（`business == "archive"`），过滤后剩下的 `business == "pgc"` 可能很少。极端情况：你这 30 天基本在看 UP 主视频 → 首页「继续观看」是空的。

**兜底规则（建议）**：正常只翻到 30 天；若过滤后 PGC 条目 `< 6`，允许继续往前翻，上限 90 天或 10 页，先取先停。这条只在冷启动首次触发。

### 其余细节（按你的策略落实）

- 清理任务：`WorkManager` 周期 7 天，约束 `requiresBatteryNotLow`，删 `view_at < now-90d`。
- 增量同步触发点：冷启动 / 下拉刷新 / 从播放页返回时更新单条。**不在每次 onResume 全量拉**。
- 页间 `delay(300ms)`，避免 `-412`。

## 7. 投屏 ⚠️ 你的推断有一处不成立，且有一条需要实测

### 7.1 「投给局域网内的 B 站 TV 端就能享受高清」→ 这个因果关系不成立

清晰度**不取决于投给谁，取决于我们请求 `playurl` 时传的 `qn` 和 `fnval`**。你有大会员，我们这边就能拿到 4K / HDR / 杜比的流。

真正的天花板在协议上：

- 4K / HDR / 杜比 只有 **DASH** 格式（`fnval=4048`），DASH 是音视频分离的自适应流，**DLNA/UPnP 的 `SetAVTransportURI` 推不了**。
- DLNA 能推的是 `durl` 格式（整段 MP4/FLV 直链），而 **`durl` 最高就是 `qn=80` = 1080P**。

所以「投屏 1080P 即可」不是妥协，**是 DLNA 路线的物理上限**。你的判断正确，只是原因和你想的不一样。

### 7.2 「能否识别局域网内的 B 站 TV 端」→ ❓ 必须实测，我不敢打包票

- 能被发现的前提是：**云视听小电视（B站TV版）对外注册了标准 UPnP/DLNA 的 MediaRenderer 服务**。
- 即使被发现，它**很可能只接受 B 站自家投屏指令**（官方 App 投到自家 TV 端时传的是 `ep_id`/`cid` 让 TV 端自己取流，不是传 URL），未必响应外部的 `SetAVTransportURI`。这个私有协议没有可靠的公开规格，且带签名、会变。
- 我尝试拉取 B 站 TV 端官方的投屏说明（`bilibili.com/read/cv1873469`）来确认，**该域名被本沙箱的出口代理拦截**，拿不到原文。

**所以这条我给你一个能一分钟出结果的办法**：M0 探针里加一个 SSDP 扫描，在你家网络跑一次，把局域网内所有 UPnP 设备的 `friendlyName` / `manufacturer` / `serviceType` 打出来。如果 B 站 TV 版在列，我们再试一次 `SetAVTransportURI`，成不成当场就知道。

### 7.3 建议的实现（等你确认）

投屏目标列表 = **标准 DLNA 设备**（jUPnP 发现，一期做）+ **B站TV版专属项**（探针证实可行才做，二期）。

推流兜底链：先直推 `durl` 直链 → 若 TV 端 403（B站 CDN 校验 Referer/UA）→ 自动切到**本机 HTTP 转发代理**，由 App 在本地起一个小服务，代 TV 端请求并注入 `Referer: https://www.bilibili.com` 和浏览器 UA。这条兜底一定能成，因为转发在我们自己手里。

**「两种投屏都支持」我同意**，只是第二种要等探针结果，一期不承诺。

## 12. Android 17 ✅ 但有几条新约束要一起处理

- `targetSdk` 跟随最新（以 Android Studio 里实际可选的为准），`minSdk` 保持 **26**（为将来的电视盒子留余地，很多 Android TV 设备停在 9~12）。

- Android 14+：前台服务必须声明类型 `mediaPlayback`。
- Android 15+：**强制 edge-to-edge**，播放页和全屏页要认真处理 insets 和刘海区。
- **预测式返回手势（Predictive Back）**：这条对我们影响最大——「详情覆盖层」和三个侧拉菜单（选集/倍速/清晰度）的关闭都靠返回键，必须用 `PredictiveBackHandler` 做带进度的动画，否则在新系统上会出现"返回预览直接跳到桌面"的观感 bug。

# 确认结论（2026-09-19，已与你逐条对齐）

## A. 登录：扫码走原生，手机号走受控 WebView ⚠️ 修正了一处设想

你的设想是「后台打开官方页面 + 自己写页面自动填写 + 二维码也自动获取显示」。拆成两半看：

### A-1 二维码：不但可以，而且**根本不需要 WebView**

扫码登录**不经过任何人机验证**，接口完全开放：

1. `GET passport.bilibili.com/x/passport-login/web/qrcode/generate` → 拿到 `url` + `qrcode_key`
2. 用 ZXing 在本地把 `url` 渲染成二维码，**完全按素笺风格画**（纸感底 + 墨色码点 + 衬线标题）
3. 每 2s 轮询 `POST /x/passport-login/web/qrcode/poll?qrcode_key=`
4. 返回码含义：`86101` 未扫 / `86090` 已扫待确认 / `86038` 已失效 / `0` 成功
5. 成功后从响应的 Set-Cookie 取 `SESSDATA` / `bili_jct` / `DedeUserID`

体验上完全由我们控制：二维码自动刷新、"已扫描，请在手机上确认"的状态切换、过期后点击重新生成。**零 WebView、零维护。**

### A-2 手机号：自动填表可以，但**滑块必须真人滑**

这是你的设想中走不通的部分，原因不是技术限制，是设计使然：

- 极验（geetest）是**行为验证**——它采集滑动轨迹、加速度、时间分布，服务端据此判定是否真人。
- 所以**隐藏在后台的 WebView 里没人能滑，我们也不能伪造轨迹**。伪造轨迹属于"绕过安全认证机制"，正是律师函点名的行为，技术上也不稳定（极验改一次就失效）。

**能做到的最好体验**（建议采用）：

| 步骤 | 在哪 |
|---|---|
| 输入手机号 | **我们的原生 UI**（素笺风格输入框） |
| 打开受控 WebView | 后台加载官方登录页，用 `evaluateJavascript` 把手机号注入表单并触发"发送验证码" |
| 滑块 | **WebView 可见，但用 CSS 注入裁剪到只剩验证码控件**，包成一个素笺风格的底部弹层。用户只需滑一下 |
| 收验证码 | 用 `SmsRetriever` 的 Consent API 自动读取（弹一次系统授权），或让用户粘贴（Android 键盘会自动提示） |
| 输入验证码 | **我们的原生 UI**，再注入回 WebView 提交 |
| 取 Cookie | 成功后从 `CookieManager` 读走，关闭 WebView |

净效果：**全程只有"滑一下"这一个动作发生在 WebView 里**，其余都是原生素笺界面。

⚠️ **代价要说清楚**：注入 JS 操作官方页面，**B 站前端改版就会失效**，需要跟着改。这是它作为"备用路径"而非主路径的原因。

### A-3 最终登录方案

| 优先级 | 方式 | WebView | 维护成本 |
|---|---|---|---|
| **主** | 扫码登录（原生渲染二维码） | 无 | 极低 |
| 备 1 | 手机号 + 验证码（受控 WebView，仅滑块可见） | 局部 | 中（随官方改版） |
| 备 2 | 手动粘贴 Cookie | 无 | 零 |

首次打开显示登录页，三种方式并列；注销后回到登录页。凭证存 `EncryptedSharedPreferences`。

## D. 入口胶囊：动态同步 ✅ 而且比原计划做得更全

**是的，这些胶囊是服务端下发的运营位**，官方一改，接口返回就变。所以可以跟着动态更新。落地分三层：

1. **拉取模块列表** — `pgc/page/cinema/tab?name=movie|tv|documentary|variety` 及番剧/国创对应接口（❓ 待 M0 探针确认返回结构）。拿到每个胶囊的图标、文案、跳转链接。
2. **按链接路由** — 指向榜单/索引/时间表的，用原生页面承接（素笺风格）。
3. **兜底 WebView** — 指向运营片单或纯活动 H5 的，用内嵌 WebView 打开官方页面。

> **这是个好转**：因为登录已经要引入 WebView，复用它之后，**之前标 ❌ 的「宝藏片单 / 好奇心周刊 / 冷门宝藏 / 综艺考古 / 康熙来了」全都不用放弃了** —— 点进去就是官方 H5，能看能点，只是那一页不是素笺风格。

- 默认：预设行在上（稳定、素笺风格），官方胶囊行在下

## E. 投屏：标准 DLNA 保底，云视听小电视作为增强 ✅

**硬约束：普通投屏任何时候都必须可用。** 所以私有协议只做增量，绝不进主路径。

```
SSDP/UPnP 扫描（jUPnP）
   ├─ 标准 MediaRenderer 设备 ──→ SetAVTransportURI 推 durl 1080P
   │                                  └─ 若 TV 端 403 → 本机 HTTP 代理注入 Referer/UA 后重推
   └─ friendlyName/manufacturer 命中「云视听小电视 / bilibili」特征
          ├─ 先按标准 DLNA 试 SetAVTransportURI ──→ 成功即走标准路（和普通设备无差别）
          └─ 失败 → 标记「该设备可能仅支持官方投屏」，不阻塞，用户可另选设备
```

- 一期交付：**标准 DLNA 投屏可用** + 设备列表中能识别并标出 B 站 TV 版
