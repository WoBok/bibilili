## 2. 鉴权方案（这是整个项目的地基）

哔哩哔哩**没有官方开放平台 API**，所有接口都是 Web / App 客户端的内部接口。可选登录方式有三种：

| 方案 | 产物 | 优点 | 缺点 | 置信度 |
|---|---|---|---|---|
| **A. TV 端扫码登录**（推荐） | `access_key` + `refresh_token` | 刷新简单、有效期长（约 30 天）、免 WBI 签名、专为「电视/自用播放器」场景设计 | appkey 权限受限，部分 Web 接口用不了；**只能拿到 TV 端可见的清晰度档位** | ⚠️ |
| **B. Web 扫码登录** | Cookie：`SESSDATA` / `bili_jct` / `DedeUserID` | 接口覆盖最全，页面数据最丰富 | 需实现 **WBI 签名**、`buvid3` 激活、`bili_ticket`；Cookie 刷新流程复杂（RSA-OAEP + correspondPath） | ✅ |
| **C. 账号密码 / 短信** | 同 B | — | 需 RSA 加密密码 + **极验滑块验证码**，实现成本极高且易触发风控 | ❌ 不推荐 |

### 推荐：A + B 双轨

- **用 B（Web 扫码）作为主鉴权**：拿到 Cookie，接口覆盖最全，详情页/频道页数据最完整。
- **同时用 A（TV 扫码）拿一个 `access_key` 兜底**：当某些 Web 接口被风控（`-352`）时切换到 App 端接口重试。
- 两者都是「扫码」，用户体验一致，UI 上只需一个二维码页（U-4 的登录界面）。

### 关键接口

| 用途 | 接口 | 置信度 |
|---|---|---|
| Web 申请二维码 | `GET passport.bilibili.com/x/passport-login/web/qrcode/generate` → `qrcode_key` + `url` | ✅ |
| Web 轮询扫码状态 | `GET passport.bilibili.com/x/passport-login/web/qrcode/poll?qrcode_key=` （0 成功 / 86101 未扫 / 86090 已扫未确认 / 86038 已失效） | ✅ |
| TV 申请二维码 | `POST passport.bilibili.com/x/passport-tv-login/qrcode/auth_code`（appkey `4409e2ce8ffd12b8` + sign） | ⚠️ |
| TV 轮询 | `POST passport.bilibili.com/x/passport-tv-login/qrcode/poll` → `access_token` / `refresh_token` | ⚠️ |
| TV 刷新 token | `POST passport.bilibili.com/api/v2/oauth2/refresh_token` | ⚠️ |
| 设备指纹 buvid | `GET api.bilibili.com/x/frontend/finger/spi` → `b_3` / `b_4` | ✅ |
| buvid3 激活（防风控） | `POST api.bilibili.com/x/internal/gaia-gateway/ExClimbWuzhi` | ⚠️ |
| 登录态校验 / 用户概要 | `GET api.bilibili.com/x/web-interface/nav` | ✅ |
| 注销（U-5） | `POST passport.bilibili.com/login/exit/v2`（带 `biliCSRF`）+ **本地清空凭证** | ✅ |

### 必须实现的两个签名

1. **WBI 签名**（Web 端大量 `x/` 接口强制要求）
   从 `nav` 响应里取 `wbi_img.img_url` / `sub_url` 的文件名 → 拼成 64 位原始 key → 按一张**固定的 64 位重排表**打乱取前 32 位得到 `mixin_key` → 把请求参数按 key 升序拼接 + `wts=<秒级时间戳>` → `w_rid = md5(query + mixin_key)`。
   `img_key`/`sub_key` **每日更换**，需缓存并按天刷新。
2. **App 端签名**（走 TV/App 接口时）
   `sign = md5(参数按 key 升序拼接 + appsec)`，参数须含 `appkey` / `ts` / `access_key`。

> 落地时把这两个签名各做成一个 OkHttp `Interceptor`，业务层完全无感。见 `03` §4。

### 所有请求必须带的 Header（否则 412 / 403）

```
User-Agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64) ... Chrome/...   # 不能用 okhttp 默认 UA
Referer:    https://www.bilibili.com
Origin:     https://www.bilibili.com
Cookie:     buvid3=...; SESSDATA=...; bili_jct=...; DedeUserID=...
```
**播放地址（CDN）的请求同样必须带 `Referer`，否则 403** —— 这是播放器接入的头号坑，见 §4.1。

## 3. 各页面数据来源

### 3.1 首页 · 历史（H-3 / H-4）—— 本项目最关键的一个问题

**你的问题**：历史要过滤掉 UP 主视频、只留影视和番剧，现有 B 站接口能不能做到？要不要自建服务器？

**答案：能做到，纯客户端即可，不需要自建服务器。**

接口：
```
GET api.bilibili.com/x/web-interface/history/cursor
    ?ps=20&type=archive&max=<上一页游标>&view_at=<上一页游标>
```
✅ 置信度高。返回的每条记录里有一个 **`history.business`** 字段用于区分内容类型：

| `business` 值 | 含义 | 本 App 是否保留 |
|---|---|---|
| `archive` | UP 主投稿视频（UGC） | ❌ **丢弃** |
| `pgc` | 番剧 / 影视 / 纪录片 / 综艺（正片） | ✅ **保留** |
| `live` | 直播 | ❌ 丢弃 |
| `article` / `article-list` | 专栏 | ❌ 丢弃 |

PGC 条目里还会带 `history.epid`、`history.business == "pgc"`、以及 `badge`（如「番剧」「电影」「纪录片」）和 `show_title`（如「第 3 话」），足够渲染卡片。

**但有一个真实的工程问题必须提前解决 ——「稀疏分页」：**

接口是**按时间倒序返回混合列表**，不支持服务端按 business 过滤。
如果你平时大量看 UP 主视频，可能翻 5 页（100 条）才捞到 3 条影视记录，首页会「加载很久还是空的」。

**对应方案（三层）：**

1. **本地 Room 缓存做「影视历史镜像」**
   建表 `pgc_history(epid, season_id, title, cover, progress, duration, view_at, ...)`。
   App 每次启动 / 下拉刷新时，从游标接口**增量拉取**（拉到 `view_at <= 本地最新 view_at` 即停），只把 `business == "pgc"` 的落库。
   首页直接读本地表 → **秒开，且永远不会是空的**。
2. **首屏保底策略**
   首次冷启动时最多连续拉 N 页（建议 N=10，约 200 条）或直到凑满 20 条 PGC 记录为止，两个条件先到先停；后台协程继续补齐历史。
3. **补充数据源**
   同时拉 `GET api.bilibili.com/pgc/web/follow/...`（追剧进度）和 `x/v2/history/toview`（稍后再看），
   与 `pgc_history` 合并去重，进一步降低首页为空的概率。

> **结论：H-4 采用方案 1+2，自建服务器不需要。**
> 本地缓存还顺带解决了「离线可见」和「首页秒开」，是纯收益。

播放进度回传（让 B 站官方端和本 App 进度互通）：
```
POST api.bilibili.com/x/v2/history/report   (aid, cid, progress, csrf)   ✅
```

## 4. 播放器（P-1 ~ P-4、F-1 ~ F-8）

### 4.1 取流

```
GET api.bilibili.com/pgc/player/web/playurl?ep_id=&cid=&qn=<清晰度>&fnval=4048&fourk=1&fnver=0
```
✅ 置信度高。`fnval` 是位掩码：
`16`=DASH　`+64`=HDR　`+128`=4K　`+256`=杜比音频　`+512`=杜比视界　`+1024`=8K　`+2048`=AV1 → 常用 **4048**。

返回 DASH 结构：`dash.video[]`（按 `id`=qn 和 `codecid` 分组）+ `dash.audio[]`（音视频**分离**）+ `dash.dolby` / `dash.flac`。

**三个必须处理的坑：**

1. **CDN 必须带 Referer**
   直接拿 `baseUrl` 去播会 **403**。必须给 ExoPlayer 配置自定义 `DataSource.Factory`，注入
   `Referer: https://www.bilibili.com` 和与取流时一致的 `User-Agent`。
2. **DASH 是 SegmentBase 形式，不能当普通 MP4 播**
   每个 Representation 有 `SegmentBase.Initialization` 和 `indexRange`。
   **正确做法：用返回的 JSON 在内存里拼一个 MPD 清单，喂给 Media3 的 `DashMediaSource`**，
   让 ExoPlayer 自己做音视频合流和清晰度切换。（不要用两个 `ProgressiveMediaSource` 硬合，会有音画同步问题。）
3. **备用 CDN**
   每个 Representation 有 `backupUrl[]`，主 URL 失败要自动切备用（PCDN 节点经常抽风）。

**降级方案**：`fnval=0` / `fnval=1` 可以拿到传统的 `durl`（整段 MP4/FLV 直链），清晰度上限 1080P。
这个方案在 **投屏（§6）** 时是必需的。

### 4.2 清晰度（F-8 清晰度菜单）

| qn | 名称 | 门槛 |
|---|---|---|
| 16 / 32 | 360P 流畅 / 480P 清晰 | 免费 |
| 64 | 720P 高清 | 需登录 |
| 74 | 720P60 | 需登录 |
| 80 | 1080P 高清 | 需登录 |

`playurl` 返回的 `support_formats[]` 里有 `new_description`（「大视界 4K」这种名字）和 `need_vip` —— **直接用它渲染清晰度菜单**，

### 4.3 手势（P-4 / F-6）

全部是纯客户端能力，✅ 无风险。在 Compose 里用一个 `pointerInput` 统一处理：

| 手势 | 行为 | 备注 |
|---|---|---|
| 单击 | 显示/隐藏控制层（F-1） | 3~5s 无操作自动隐藏 |
| 双击左 / 右 | 快退 / 快进 **N 秒**（N 默认 10，可设） | 需要「双击连击」计数：连续双击应累加（-10s → -20s → -30s） |
| 长按 | 以 **M 倍速**播放（M 默认 2.0，可设），松手恢复 | 长按时显示「M 倍速播放中 ⏩」浮层 |
| 横向拖动 | 拖动进度（带缩略图预览可选） | 与双击冲突，靠 `detectHorizontalDragGestures` 的阈值区分 |
| 左半屏纵向拖动 | 亮度 | 可选 |
| 右半屏纵向拖动 | 音量 | 可选 |

> **实现提示**：`detectTapGestures` 的 `onDoubleTap` 与 `onLongPress` 同时用时，长按会被 `onPress` 先截获。
> 建议用 `awaitEachGesture` 手写状态机，或把 `onLongPress` 的触发阈值设为 300ms 并在 `onPress` 里挂 `tryAwaitRelease()`。

### 4.4 全屏三点菜单（F-4 / F-5）

| 功能 | 实现 | 风险 |
|---|---|---|
| **定时关闭** | 不开启 / 15 / 30 / 60 分钟 / 自定义 **+ 建议加「播完本集」** | ✅ 无 |
| **跳过头尾** | 开关 | ⚠️ 见下 |
| **自动连播** | 开关；播完自动播 `episodes[]` 里的下一集，跨季时自动跳下一季首集 | ✅ 无 |
| **快进步长**（原「快进秒数」，建议改名） | 5 / 10 / 15 / 30 秒 | ✅ 无 |
| **长按倍速** | 与倍速菜单**同一份档位**：0.5/0.75/1/1.25/1.5/1.75/2/2.5/3，默认 2.0 | ✅ 无 |
| **循环播放** | 单集循环 / 列表循环 / 不循环（截图里有，建议保留） | ✅ 无 |

**「跳过头尾」的数据来源问题** ⚠️：
片头片尾的时间点来自 `playurl` / `view` 响应里的 `skip: { prologue: {start, end}, epilogue: {start, end} }` 字段（App 端接口里较常见），
**但很多剧集这个字段是空的**。

**三层兜底：**
1. 有 `skip` 字段 → 直接用；
2. 没有 → **让用户在当前集手动标记「片头结束」「片尾开始」**，按 `season_id` 存进 Room，**同一季的其它集自动复用**（这是最实用的方案，很多第三方播放器都这么做）；
3. 都没有 → 菜单项置灰并提示「本剧集暂无片头片尾信息，可长按手动标记」。

**F-5 设置的作用域**：「快进步长」「长按倍速」是**全局偏好**（DataStore），竖屏页和全屏页读同一个 Flow；
「倍速」「清晰度」是**会话级**（按 `season_id` 记忆，DataStore/Room）；「定时关闭」是**一次性**（进程内，退出即清）。

### 4.5 竖屏页布局（P-1 ~ P-3）

自上而下：播放器（16:9 固定）→ Tab（简介 / 选集）→ 内容。
右上角收藏 + 投屏、左上角返回 —— 竖屏时叠在播放器上（和截图一致），滚动时不动。

**D-1「详情覆盖播放器下方」** 的实现：不是新 Route，而是在播放器下方的容器里放一个
`AnimatedVisibility` + `slideInVertically` 的全覆盖层（Compose `Box` 内的兄弟节点），播放器**不停不缩**，符合你的原话「覆盖播放器下方的页面」。

## 5. 豆瓣评分（D-3）—— ⚠️ 需要你拍板

**结论：技术上能做，但没有一条「干净」的路。**

豆瓣自 2019 年起**关闭了开放 API**（api.douban.com/v2 需要 apikey 且已停止发放）。可选路径：

| 路径 | 做法 | 问题 |
|---|---|---|
| A. 豆瓣 App 内部接口（frodo） | 走 `frodo.douban.com/api/v2/...`，需固定 apikey + 签名 | 灰色地带；随时可能封禁；apikey 轮换 |
| B. HTML 抓取 | `https://www.douban.com/search?cat=1002&q=<片名>` → 解析列表页 → 进详情页取评分 | 强反爬（验证码、IP 封禁）；HTML 结构变了就挂；移动端解析 HTML 成本高 |
| C. 第三方聚合 API | 用别人搭的镜像服务 | 可用性完全不可控，且等于把你的请求交给第三方 |
| D. **不做豆瓣，改用 B 站自带评分** | `view/web/season` 里的 `rating.score` + `rating.count` | ✅ 零风险、零成本 |

**另一个绕不开的问题：匹配准确率。**
就算能抓到豆瓣，还要**把 B 站的剧集匹配到豆瓣条目**上。可用的匹配键只有：`origin_name`（原名）+ `publish.pub_time` 的年份 + `areas`（地区）。
中文译名、"第 N 季"、纪录片同名等情况下**误匹配率不低**，展示一个错的评分比不展示更糟。

**我的建议（供讨论）：**
> **一期不做豆瓣，详情页直接用 B 站评分（截图里的 9.6 就是它）。**
> 二期把它做成一个**可插拔的「外部评分源」模块**（`RatingProvider` 接口）：默认关闭，在设置里手动开启；
> 抓取放在后台 + 本地长缓存（≥7 天）+ 失败静默隐藏 + **只在原名和年份都能对上时才显示**。
> 这样既满足你的需求，又不让一个不稳定的外部依赖拖垮详情页。

**请你确认：一期做 / 二期做 / 不做？**

## 6. 投屏（P-2 / F-3）—— ⚠️ 需要你拍板

**结论：能做，但必须在「清晰度」和「复杂度」之间二选一。**

核心矛盾：
- B 站高清晰度片源是 **DASH（音视频分离 + SegmentBase）**；
- **绝大多数 DLNA/UPnP 电视和盒子不支持 DASH**，只认单个 HTTP 直链（MP4/TS）；
- 而且 B 站 CDN **要求 Referer**，投屏时是电视去请求 URL，**电视不会带 Referer → 403**。

| 方案 | 做法 | 清晰度上限 | 复杂度 |
|---|---|---|---|
| **A. 降级投屏**（推荐一期） | 投屏时**重新用 `fnval=1` 取 `durl` 直链**（整段 MP4），推给 DLNA 渲染器 | **1080P（qn≤80）** | 低 |
| B. 本地转封装代理 | App 内起一个 NanoHTTPD 本地服务，边下 DASH 边合流成 TS/MP4，把 `http://<手机IP>:<port>/xxx` 推给电视，同时由代理注入 Referer | 4K/HDR 可行 | **高**（实时 remux + 带宽 + 发热） |
| C. Google Cast | 用 Cast SDK | 只支持 Chromecast，且同样有 DASH/Referer 问题 | 中 |

**推荐：一期做方案 A**，UI 上明确提示「投屏最高支持 1080P」。
库选型：`jUPnP`（Cling 的活跃分支，Cling 已停止维护）做设备发现 + AVTransport 控制。

> 如果发现 `durl` 直链在电视上也 403（部分 CDN 会校验 Referer），
> 那就必须退到 **方案 B 的简化版**：本地起一个**纯转发代理**（只加 Referer 头、不做 remux），把代理地址投给电视。
> 这比完整 remux 简单得多，是一个很好的中间态。**这条路径需要实测确认。**

## 7. 风控与稳定性（必须提前设计）

| 现象 | 错误码 | 原因 | 对策 |
|---|---|---|---|
| 请求被拦截 | `-412` | UA 异常 / 缺 buvid / 频率过高 | 伪装浏览器 UA、带全套 Cookie、请求间隔 ≥300ms、失败退避重试 |
| 触发风控校验 | `-352` | 缺 WBI 签名 / `bili_ticket` / buvid3 未激活 | 正确实现 WBI；启动时激活 buvid3；必要时切 App 端接口 |
| 账号未登录 | `-101` | Cookie 失效 | 静默刷新 → 失败则跳登录页 |
| 地区限制 | `-10403` | 版权分区（港澳台/海外限定） | 明确提示「该内容所在地区不可观看」，不要显示成"加载失败" |
| 会员内容 | `-10403` / 试看 | 非大会员 | 读 `vipStatus`，UI 提前置灰并标角标 |
| 接口结构变更 | — | B 站改版 | **所有 JSON 解析用 `ignoreUnknownKeys = true` + 字段全可空 + 模块级 try/catch**，单模块失败不白屏 |
